# SITA OS — Observability & Diagnostics

This document describes the **canonical** native observability surfaces.
There is one collector chain, one heartbeat path, one support bundle
format. Do not introduce parallel diagnostics pipelines.

## Native log surfaces

| Source | Path / journal unit |
|---|---|
| Boot | `journalctl -b` |
| First boot | `sita-firstboot.service` + `/var/log/sita-firstboot.log` |
| Runtime shell | `sita-runtime.service` (Electron via `shell-watchdog.sh`) |
| Updater | `sita-updated.service` + `.timer` |
| Recovery | `sita-recovery.service` / `sita-recovery-shell.service` |
| Verity events | `dmesg` (kernel) |
| Shell crashes | `/var/log/sita/crashes/shell-*.log.gz` |
| Crash dumps (Electron renderer) | `/var/lib/sita/crashes/*.dmp` → `crash-report-ingest` edge fn |

## Diagnostics collectors

All collectors live in `os/diagnostics/` (installed at
`/opt/sita/diagnostics/`) and write to `/var/lib/sita/diagnostics/`
(falls back to `/tmp/sita-diagnostics/` when root is read-only). They
are idempotent and safe to run any time.

| Collector | Output JSON | What it captures |
|---|---|---|
| `collect-boot-health.sh` | `boot-health.json` | kernel, firmware, secure-boot, slot, blessing, time-to-userspace, kernel error count, verity state |
| `collect-runtime-health.sh` | `runtime-health.json` | service states, X server, Electron PID/RSS, crash counter, safe-mode flag |
| `collect-update-health.sh` | `update-health.json` | active slot, pending update, last apply result, last bundle verification, rollback armed |
| `collect-service-failures.sh` | `service-failures.json` + `failed-unit-logs/<unit>.log` | every failed systemd unit + last 50 journal lines |
| `emit-runtime-status.sh` | `runtime-status.json` | one-shot heartbeat (consumed by `deploy/metrics-agent.sh`) |
| `recovery-status.sh` | `recovery-status.json` | full recovery snapshot (slot, verity, crashes, failed units) |

Run all four heavy collectors at once:

```bash
sudo /opt/sita/diagnostics/collect-boot-health.sh
sudo /opt/sita/diagnostics/collect-runtime-health.sh
sudo /opt/sita/diagnostics/collect-update-health.sh
sudo /opt/sita/diagnostics/collect-service-failures.sh
# or, from the source tree:
npm run os:diag:all
```

## Heartbeat path (cloud reporting)

There is **one** metrics agent: `deploy/metrics-agent.sh`. It runs on a
5-minute schedule and folds the canonical native runtime status
(`emit-runtime-status.sh`) into its existing payload as `native_runtime`,
then POSTs to the `os-status` edge function.

```
emit-runtime-status.sh → /var/lib/sita/diagnostics/runtime-status.json
                              │
                              ▼
                  deploy/metrics-agent.sh   (adds CPU/RAM/disk/docker)
                              │
                              ▼
                  POST /functions/v1/os-status
```

No second agent. No alternate transport.

## Support bundle

Generated by `os/scripts/generate-support-bundle.sh`. Canonical
on-device command: `sudo sita-support-bundle`. From recovery mode use
`sudo sita-recovery-collect` (writes to `/tmp/sita-support` when `/var`
is read-only).

Bundle layout:

```
bundle/
  meta/host.json              build/version/kernel/uptime/slot/channel
  meta/verity-status.txt
  meta/attestation.json
  logs/journal-current-boot.log
  logs/journal-previous-boot.log
  services/<unit>.status      sita-firstboot, sita-runtime, sita-updated, sita-recovery
  services/<unit>.log
  state/etc-sita/             /etc/sita snapshot
  state/rollbacks/            /var/lib/sita/rollbacks snapshot
  state/native-state/         /var/lib/sita/state (crash counter, safe-mode marker)
  state/boot-entries.txt
  diagnostics/recovery-status.txt    fresh recovery-status snapshot
  diagnostics/*.json                 fresh collector outputs
  diagnostics/failed-unit-logs/      per-unit logs from collect-service-failures
  crashes/                           /var/log/sita/crashes (gzipped)
```

Output: `/var/lib/sita/support/sita-support-<host>-<ts>.tar.zst`
(or `$SITA_SUPPORT_DIR` if overridden).

Secrets are redacted in-place (JWTs, Stripe keys, license keys, generic
`password=`/`token=` patterns) before archival.

## Shell failure observability

The Electron shell is launched through `os/runtime/shell-watchdog.sh`
(via `xinit /opt/sita/shell/launch.sh`). On crash:

1. Watchdog increments `/var/lib/sita/state/shell-crash-count`.
2. Writes a gzipped log to `/var/log/sita/crashes/shell-<ts>.log.gz`
   containing exit code, version, slot, and last 200 journal lines.
3. ≥ `SITA_CRASH_THRESHOLD_SAFE` (default 3) within
   `SITA_CRASH_WINDOW_SEC` (default 60) → marks safe-mode for next launch.
4. ≥ `SITA_CRASH_THRESHOLD_RECOVERY` (default 5) → starts
   `sita-recovery-shell.service` on TTY7 and exits 69.

systemd `OnFailure=sita-recovery-shell.service` provides the same
fallback when the unit itself fails to start.

## Phone-home (optional, opt-in at first boot)

If enabled, the device sends:

- channel + version + slot
- last rollback timestamp (no payload)
- crash counts (no stack traces)
- the `native_runtime` heartbeat block (status + flags only)

…to `supabase/functions/crash-report-ingest` and `os-status`. Disabled
by default.
